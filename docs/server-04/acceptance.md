# Ревизия восстановления server-04

06.11.2026 · `d4-tihiy-dom-server-04`. Авторская проверка, передача на повторную независимую приёмку.
Server-03 не принят из-за подтверждённого дефекта отказа restore. Прочитаны дополнение задания 10,
acceptance.md, restore_probe.py и restore-probe.json из docs/review-coordinator/server03; они не запускались с записью
в папку ревьюера и не изменялись. Визуал/API заявки/фото/доставка не переделывались.

## Исправление

Ранее backup проверялся только по integrity и именам таблиц, а initialize запускался уже на заменённом реестре.
Инициализация несовместимой схемы падала после переноса: safety-copy не сохраняла работоспособность текущей базы.

Теперь Store.restore:

1. Читает исходник только для чтения и копирует в отдельный приватный `.restore-*` внутри каталога данных.
   Негативные тесты используют только временные каталоги; настоящий data/backups не открывается SQLite.
2. Проверяет подготовленный снимок: integrity_check, всю схему SQLite (DDL таблиц, колонки/типы/NOT NULL,
   PK/UNIQUE/FK/CASCADE/default, индексы и отсутствие дополнительных объектов), user_version/application_id,
   encoding/page_size и foreign_key_check. Эталон создаётся из штатного SCHEMA, whitespace нормализуется.
3. Выполняет initialize/recovery и cleanup на временном снимке; повторно проверяет результат.
4. Только после успеха переносит снимок в рабочую базу SQLite Backup API порциями по 16 страниц.
   SQLite держит транзакцию назначения до завершения; отказ до SQLITE_DONE откатывает её.
   При ожидании/незавершённом копировании установлен предельный бюджет 10 секунд.
5. После commit не вызывает initialize/cleanup рабочего реестра. Очистка временного каталога не поднимает ошибку
   из-за удаления файлов после успешного commit (`ignore_cleanup_errors=True`).

Поддержка атомарного отката основана на [контракте SQLite Backup API](https://www.sqlite.org/c3ref/backup_finish.html)
и проверена внедрением исключения после реально перенесённой части страниц, до SQLITE_DONE.
Это транзакционный перенос SQLite, не файловый rename поверх открытой WAL-базы.
Допускается штатный формат backup D4; произвольные косметически/семантически похожие схемы и миграции не обещаются.

CLI больше не вызывает initialize текущего реестра перед проверкой restore: даже `processing`-статусы при отказе
остаются прежними. После Store.restore нет отдельного cleanup, который мог бы завершиться ошибкой уже после замены.
Известные ошибки совместимости/SQLite/файлов/таймаута дают exit 2 и короткое сообщение без traceback и данных.
Safety-copy по-прежнему создаётся приватно и сохраняется при отказе.

|---|---|
| Store: четыре имени таблиц, неверные колонки | Отказ до записи, исходный реестр работоспособен |
| Store: утрата UNIQUE/NOT NULL/FK-CASCADE, неверный default, посторонний trigger | Каждый вариант отвергнут до записи |
| Store: повреждённый файл, orphan photo, другая user_version | Отказ, исходные данные и квитанция сохранены |
| Store: ошибка после изменения временной копии в initialize | Текущая заявка/фото/два задания/квитанция без изменений |
| Store: ошибка после cleanup временной копии | Текущий реестр без изменений |
| Store: ошибка после первых 16 страниц переноса | remaining > 0 и remaining < total; перенесённая часть откатилась |
| Работоспособность после отката | Квитанция читается, новая заявка затем успешно сохраняется |
| Реальный CLI `python -m server.manage restore …` | Неверные колонки/UNIQUE/FK и повреждённый файл дают exit 2 |
| CLI: ошибки initialize/cleanup/частичного копирования | В отдельных процессах внедрена ошибка; exit 2, без ложного успеха/traceback |
| Сохранность после каждого отказа CLI | Полные данные заявки, байты фото, оба задания, rate_events и квитанция совпали с исходными |
| Safety-copy при отказе CLI | Одна корректная приватная копия 0600, содержимое совпало с исходным реестром |
| Положительные Store и обычный CLI | Совместимый backup успешно восстановлен; processing источника подготовлен в unknown до переноса |
| Оригинал backup | При успешном restore исходный файл не изменён; временные каталоги после опытов удалены |

Сравнение сохранности — не только числа строк: SHA-256 от всех значений/байтов всех строк четырёх таблиц,
integrity_check и чтение квитанции с исходным ключом. Для отрицательных Store-случаев повторено также HTTP-чтение
квитанции через TestClient. Ключи/контакты/BLOB не записываются в доказательства.
CLI-сбои подготовки/копирования внедряются только одноразовым тестовым процессом, production flags/endpoints не добавлены.
Тестовые процессы запускают копию server/ с ROOT во временном каталоге, а не используют настоящий реестр.
