## Блокер: отказ restore повреждает рабочий реестр

`server/store.py:146` (`Store.restore`): до записи проверяются integrity_check и наличие четырёх имён таблиц,
затем `backup.backup(target)` заменяет реестр. Проверка через `initialize()` идёт уже после замены.
Полная совместимость колонок/ограничений и работоспособность восстановленного реестра заранее не подтверждены.

Независимая проба `restore_probe.py` работает только в собственном TemporaryDirectory:

1. Создан корректный синтетический реестр с заявкой и фото. Корректный backup/restore успешно повторён.
2. Создан другой исправный SQLite (`integrity_check=ok`) с четырьмя требуемыми именами таблиц,
   но несовместимыми колонками `unrelated`.
3. `restore` допустил его до копирования и завершился `OperationalError: no such column: stamp`.
4. После отказа запрос исходной заявки невозможен: рабочая схема уже заменена.

`restore-probe.json`: отказ обнаружен, но **working registry preserved after rejection = false**.
CLI создаёт отдельную страховочную копию перед restore; это позволяет ручное восстановление, но не сохраняет
работоспособность текущего реестра после неуспешной команды. Ошибка актуальна и для случайно выбранного backup
другой версии, а не только для специально изготовленного файла. Авторское утверждение о проверке schema недостаточно.

Требование: проверить совместимость до изменения рабочего реестра; выполнить восстановление так, чтобы отказ проверки,
инициализации или замены не оставлял текущую базу повреждённой. Проверять не только имена таблиц.
Нужны отрицательные тесты несовместимых колонок/ограничений, повреждённого файла и сбоя в процессе восстановления;
после каждого отказа существующие заявка/фото/два задания и квитанция должны оставаться работоспособными.
Добавить реальный CLI-тест отказа, а не только успешный Store.restore. Сохранить проверку lock и приватные safety-backups.
Новые зависимости для этой доработки не требуются.
