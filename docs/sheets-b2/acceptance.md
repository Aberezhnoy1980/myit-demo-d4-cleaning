# Sheets B2: офлайн-подготовка для независимой проверки

06.11.2026 · `d4-tihiy-dom-sheets-b2-07`. Авторский протокол, статус «принято» не присваивается.
Основание — задание 13, принятый B1-06 и свидетельства координатора о единственном live-тесте Telegram
и подтверждении владельца. Прежнее разрешение Telegram исчерпано, повторных отправок не было.

## Область реализации

`server/sheets.py`: только офлайн-контракт с явными OfflineAuthorization и httpx.MockTransport.
Он не подписывает JWT, не выполняет OAuth, не использует ADC/gcloud/Keychain и не строит реальный HTTP-транспорт.
Искусственная авторизация не выдаётся за проверку настоящего Google SDK.

Новая `row_for_submission` строит девять RAW-строк из конкретной сохранённой и неистёкшей заявки:
UUID, UTC accepted_at (секунды, Z), sofa, size, material, description, synthetic_channel, synthetic_contact, photo_count.
Время берётся из created, не из момента отправки; 1–3 фото считаются в локальной БД, сами байты не читаются/не передаются.
Контакт проверяется Lead и остаётся синтетическим. Формульные префиксы RAW не изменяются; CSV-защита остаётся отдельно.
Старый sheets_row с семью полями сохранён только как исторический helper и в B2 не используется.

Фиксированы HTTPS sheets.googleapis.com, лист Leads и предел A1:I201 (200 строк данных).
Каждое чтение ограничено диапазоном и 2 МиБ JSON; строки/ячейки имеют конечные лимиты, redirects/encoding отказаны,
trust_env=False, timeout connect 3/write 5/read 5/pool 1 с, проверка 15 с между чанками.
Это фазовые таймауты, не жёсткий системный таймер всего процесса. До 4 HTTP-вызовов одного send:
шапка → поиск в A2:I201 → append → чтение одной строки. Найденная точная строка обходится двумя GET без POST.

Шапка должна точно совпасть с девятью именами HEADERS. Не перестраиваем лист, не исправляем конфликт автоматически.
Несколько UUID/строка с тем же UUID и иными данными, дыры перед концом или заполненный лимит останавливают append.
Передача — values.append, RAW/INSERT_ROWS. updatedRange не используется как URL: проверяется тот же spreadsheetId
в двух полях ответа, Leads, ровно A:I, ожидаемый следующий номер <=201, updatedRows/Columns/Cells = 1/9/9.
Читается только заново построенный разрешённый диапазон; сравниваются все девять исходных значений.

Это ограниченный протокол отдельного контролируемого листа, не exactly-once при его внешнем редактировании.
Данные за I201 не сканируются; ресурс должен принадлежать стенду и не иметь иных писателей/данных вне диапазона.
Поведение настоящего Sheets и SDK предстоит проверить после отдельного разрешения установки/ресурса/live.

## Состояния, повторы и независимость

Схема SQLite не меняется. Используются прежние deliveries, префиксы mock_/live_ и simulated.
Первый claim привязывает spreadsheet_id, Leads, лимит и service account хэшем. Ключ/токен в binding не входят:
ротация той же учётной записи не создаёт дубль. Подмена ресурса/учётной записи после claim запрещена.
Старые simulated-задания не переводятся в live. Только выбранный UUID, без очереди/фонового отправителя.

Перед HTTP коммитится processing. При аварии следующий адресный send переводит его в unknown без HTTP.
При неизвестном результате или неудачной локальной фиксации повтор append блокируется.
Сверка reconcile — только два GET (шапка/ограниченный диапазон), максимум 3 явные сверки на задание:
одно полное совпадение → delivered, отсутствие/дубли/конфликт/ошибка → остаётся unknown, без права новой записи.

| Фаза/исход | Политика |
|---|---|
| GET до append: connect/read/write/5xx | pending, ручная попытка после 30 с, всего до 3 |
| Явный валидный 429 | pending, Retry-After целое 1–3600 с, всего до 3 |
| Явный 400/401/403/404 | failed, без refresh/автоматического повтора |
| Истёкшая/ошибочная искусственная авторизация до HTTP | failed, без поиска других credentials |
| Append connect/pool отказ до передачи | pending, ручная попытка после 30 с |
| После начала append: read/write timeout, разрыв, 5xx, плохой JSON/диапазон/ack | unknown, append повторно запрещён |
| Успешный append, затем любой отказ чтения (включая 401/403/429/connect) | unknown, только сверка, не новый append |
| Точная существующая строка/успешное чтение после append | delivered; повтор команды не вызывает HTTP |
| SDK отсутствует или ещё не принят | Live CLI exit 2 до конфигурации/реестра/сети |

Существующий registry flock держится на протяжении CLI, preflight, HTTP и локальной фиксации.
Конкурирующий отправитель/backup/web-сервер не допускаются. Внутренний send_one требует lock вызывающей стороны.
Тестовые модели live используют monkeypatch только в тестовых процессах с MockTransport; настоящих live-вызовов нет.

Заявка/байты JPEG/строка Telegram не меняются от любого исхода Sheets. Квитанция строит смысл каждого канала отдельно:
живой Sheets больше не сопровождается жёстким «Google Sheets не подключены» из Telegram-сообщения.
Тестовый канал отмечен по имени, unknown не называется успешной записью.

## Настройка и закрытый live-путь

Пустой `.env.sheets.example` отделён от строгой Telegram-настройки. Только этот шаблон явно разрешён Git/manifest;
реальные .env*, .secrets/, *.credentials.json исключены. Единственный будущий путь ключа:
`/Users/alex/myit/demo/Landing/d4-cleaning/.secrets/sheets-service-account.json`, вне public/Git/manifest.
В текущем этапе .secrets и ключ не создавались, настоящие конфигурации не читались и не изменялись.

Парсер: пять разрешённых ключей, до 4096 байт, UTF-8, literal значения без shell/source/eval/export/кавычек.
Файл принадлежит текущему пользователю, обычный, 0600/0400, без symlink. Pure-проверка будущего service_account JSON
проверяет тип, заранее заданный client_email, фиксированный token_uri, universe_domain и отсекает неизвестные поля/endpoint.
Она не проверяет криптографическую действительность ключа и не передаёт его SDK в этом срезе.

`sheets-send`/`sheets-reconcile --submission-id … --execute-live` — зарезервированные будущие команды.
Без флага нет чтения config. Даже с флагом require_live_sdk останавливается до config/data:
SDK сейчас отсутствует; одно его появление также не включает live (второй явный отказ до реализации/приёмки).
build_live_adapter дополнительно закрыт. HTTP приём/импорт/стартап не вызывают Sheets.

Пример будущего интерфейса, **в текущем срезе только безопасный отказ, не действующая OAuth-интеграция**:

```sh
.venv/bin/python -m server.manage sheets-send --submission-id ОДИН_СОГЛАСОВАННЫЙ_UUID --execute-live
.venv/bin/python -m server.manage sheets-reconcile --submission-id ТОТ_ЖЕ_UUID --execute-live
```

Не передавать ключи/JSON/bearer/JWT в argv, чат или отчёты. Стандартные HTTP-логи временно выключены
на срок клиента прежним защитным контекстом с восстановлением logging.disable. Полные исключения/ответы не сохраняются.
В БД только безопасные reason enum, binding, счётчик сверок. Проверены сырой/JSON/закодированный искусственные маркеры.
Исключение искусственного provider не является проверкой поведения настоящего SDK — это отдельный следующий этап.

## Что передаётся и что остаётся

Исходники Sheets/конфигурации, новые тесты, адресные CLI-ветки и независимый текст каналов; пустой шаблон/исключения;
README/integration/live-resources/dependencies/report, JUnit и проверка сохранности.
Предложение пакетов, ограничения и план SDK-проверки — dependencies.md; это не проверенный установленный lock.
Настоящий OAuth, его повторы/маскирование и совместные импорты без установки проверить невозможно и не заявляется.

Следом — независимое офлайн-ревью, отдельное решение о пакете/установке, затем приёмка официального SDK на искусственных
значениях. Только после этого — отдельные разрешения на Google-ресурс, чтение конкретной авторизации и одну строку+чтение.
Повтор Telegram для B2 запрещён. Срок внешней строки/её ручное удаление согласуются отдельно; локальный TTL Google не чистит.
Manifest исключает себя, private/runtime, кэши и docs/review-coordinator. После его пересборки запись в срез прекращается.
