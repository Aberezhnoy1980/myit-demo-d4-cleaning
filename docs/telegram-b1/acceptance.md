06.11.2026 · `d4-tihiy-dom-telegram-b1-05`. Авторский протокол, не независимая приёмка.
Основание — задание 12 и принятый координатором server-04 в проверенном объёме.
Реальные секреты не читались, Telegram/Google не вызывались, ресурсы не создавались.
Установок, Git/remote, публикации, дополнительных агентов и изменений business/общего хэндофа нет.

## Подготовленная реализация

- `server/telegram_config.py`: строгий literal key=value парсер трёх ключей; отдельный файл `.env`
  только по явному вызову, без environment/Keychain fallback, symlink, shell/source/eval, кавычек и подстановок.
  Текущий владелец, обычный файл, права 0600/0400, до 4096 байт, UTF-8. Ошибки/repr скрывают значения.
  `.env.example` пустой и выключенный; только он разрешён исключением `.gitignore` и manifest.
- `server/telegram.py`: один sendPhoto на фиксированный HTTPS api.telegram.org. Получатель — из серверной настройки,
  не из формы. Redirect запрещён, trust_env=False, HTTP retries=0. Отправляется первый сохранённый JPEG
  только выбранного UUID; проверены возраст заявки, синтетическая схема, формат/размер/метаданные фото.
  Подпись: UUID, тип/размер/материал и пометка демо; без контакта, свободного текста, URL и ключа квитанции.
- `server/manage.py`: будущая команда на один UUID, без автоматического обзора очереди. Без `--execute-live`
  нет даже чтения конфигурации; дополнительно обязателен D4_TELEGRAM_LIVE=1. Во время операции держится тот же
  эксклюзивный `.server.lock`, что у сервера/backup/restore. Не ослаблены lock и принятый restore.
- Схема SQLite и исходная транзакция сохранения не менялись. Статусы `mock_*` (simulated=1) и `live_*` (0)
  разделены. Старые simulated задания и mock-задания никогда не повышаются до live. Первое выполнение фиксирует
  SHA-256 привязки bot ID + chat_id, без токена/получателя в строке задания. Ротация токена того же бота допустима.
- Перед HTTP коммитится processing с увеличением attempts; после — безопасный исход. Остаточный processing
  при следующем адресном CLI становится unknown без отправки; квитанция уже показывает неизвестный результат.
  Provider message_id хранится только в приватном служебном JSON, не в клиентском ответе/протоколе.
- `server/delivery.py`, DTO Store и текст UI: квитанция различает отключённый/тестовый/живой режимы и не приравнивает
  создание сообщения к прочтению. Сохранённые поля, JPEG и независимый job Sheets не меняются исходом Telegram.

Внутренний `send_one` требует lock вызывающего CLI; его прямой конкурентный вызов не является поддержанным интерфейсом.
Общий logging.disable временно закрывается на время HTTP-клиента в отдельном CLI-процессе и восстанавливается в finally.
Это исключает стандартные httpx/httpcore логи с token в пути; полные Request/Response/Exception/description
не сохраняются и не печатаются. Приложение не обещает защиту от внешнего отладчика или дампа памяти процесса.

Таймауты connect 3 с / write 5 с / read 5 с / pool 1 с; ответ до 64 КиБ, encoding только identity.
Дедлайн 15 с проверяется между чтениями: фазовые ограничения HTTPX не являются жёстким системным общим таймером.

## Политика исходов

| Условие | Результат и повтор |
|---|---|
| 200 + ok + точный chat.id + положительный message_id + валидный photo | delivered: Bot API создал сообщение; человек не подтверждён |
| Повтор уже delivered | Без второго HTTP, возвращается прежний смысл подтверждения |
| ConnectError/ConnectTimeout/PoolTimeout до передачи | pending, ручной повтор не ранее 30 с |
| Явный 429, ok=false, совпавший error_code, целый retry_after 1–3600 | pending, ручной повтор после указанной задержки |
| Попытка №3 с разрешённым retry-исходом | failed, лимит исчерпан |
| Явный валидный 400/401/403/404 | failed, без повтора |
| Read/write timeout, разрыв, 5xx, malformed/truncated JSON, неполный успех, другой получатель, redirect | unknown, повтор запрещён |
| Сбой записи после HTTP / аварийный processing | unknown, повтор запрещён |
| Нет config, live выключен, чужой бот/получатель после claim, истёкшая/неверная заявка или фото | Отказ до HTTP |

Всего максимум 3 явные попытки на задание. Никакого автоматического повтора, фоновой доставки или гарантии exactly-once.
Unknown требует проверки владельцем, а не повторного запуска команды. Исход Google не меняется.

Для прежнего фото-декодера нужен доступ к `/bin/ps`; полный прогон выполнен с этим доступом вне командной песочницы.
Ни Telegram, ни другие live-сервисы из-за этого не использовались.

Все B1 HTTP-вызовы — httpx.MockTransport; socket connection/DNS запрещены и в CLI-процессах.
Ветка live моделируется только на временных искусственных данных с подменой HTTPTransport на MockTransport;
это не доказательство живого получения. Явный MockTransport в обычном адаптере всегда даёт test/simulated=1.
Настоящий `.env` ни один тест не читает: проверяется только шаблон или искусственный временный файл.

| Группа | Проверено |
|---|---|
| Настройка | Пустой шаблон, неизвестные/дублированные ключи, shell/URL-инъекции, права, symlink, отсутствие fallback |
| Контракт | POST/sendPhoto/фиксированный host+получатель, JPEG multipart, ограниченные timeout, отсутствие контакта/ключа в теле |
| Ответы | 200/400/401/403/404/429/500, другой chat, неполный/невалидный JSON, фото неверной формы, обрыв потока, лимиты/encoding/redirect |
| Ошибки | Connect/pool/read/write и прочие неопределённые сбои; уникальный искусственный token-маркер отсутствует в логах/stdout/stderr/DTO/metadata |
| Повторы | 429 задержка, неправильный retry_after, максимум 3, привязка бота/получателя, повтор успеха без HTTP |
| Неопределённость | Остаточный processing, сбой записи после ответа, запрет повторов unknown |
| Границы | Неверный/истёкший UUID, повреждённый JPEG, только выбранный ID, legacy simulated/mock нельзя превратить в live |
| Независимость | Сохранены заявка, JPEG, Sheets; receipt/replay показывает текущий безопасный результат |
| CLI | Без флага конфигурация не читается; отсутствие config останавливает до транспорта; секретов нет в ошибке |
| Конкуренция | Первый CLI удерживает lock внутри mocked HTTP; второй CLI и backup отказали; повтор после завершения не вызывает HTTP снова |
| HTTP и импорт | Старт/POST только сохраняют, Telegram transport не создаётся; новых импортных/фоновых отправок нет |
| Регрессии | Все прежние SQLite/restore/фото/API-тесты пройдены |

## Будущий один live-тест: отдельно согласовать, сейчас не выполнять

1. Завершить независимое офлайн-ревью этого среза. Владелец подтверждает выделенного бота и одну закрытую группу,
   разрешение фото обычному участнику; admin/privacy-off/webhook не нужны. Способ определения chat_id согласуется
   отдельно, без фонового чтения переписки. Никакие getMe/getChat/getUpdates в этом срезе не выполнялись.
2. Отдельно разрешить чтение `/Users/alex/myit/demo/Landing/d4-cleaning/.env`, конкретного получателя, одну свежую
   синтетическую заявку и первый JPEG, один sendPhoto и методы подтверждения. Секреты владелец вводит локально
   по `.env.example` с LIVE=1 и правами 0600; значения не передаются в чат/argv/логи. Не выполнять source .env.
3. Сохранить новую заявку через локальную форму, получить её UUID/квитанцию, остановить сервер. Не запускать simulate
   для выбранной заявки: simulated не превращается в live. Проверить возраст <24 ч, квитанцию лучше проверять в течение 1 ч.
4. Только после разрешения выполнить один раз (вместо placeholder — один утверждённый UUID):

```sh
cd /Users/alex/myit/demo/Landing/d4-cleaning
.venv/bin/python -m server.manage telegram-send --submission-id ОДИН_СОГЛАСОВАННЫЙ_UUID --execute-live
```

5. Безопасный вывод CLI и затем квитанция после запуска сервера подтверждают только API-результат.
   Владелец отдельно смотрит согласованную группу и подтверждает единственное фото/подпись с тем же UUID.
   В доказательствах — UUID, безопасный статус, время и отдельное подтверждение владельца; без URL с token,
   полного ответа, chat_id, receipt_key и переписки. При unknown остановиться и сначала проверить группу.
6. До запуска согласовать срок внешнего сообщения и его очистку. После подтверждения владелец удаляет тестовое сообщение
   вручную в согласованный срок; deleteMessage в адаптере отсутствует и без отдельного разрешения не вызывается.
   Владелец локально возвращает LIVE=0. Локальные данные удаляются по прежнему TTL 24 ч/cleanup, backup тоже имеет TTL 24 ч;
   при выключенном сервере — только при следующем запуске/явной cleanup --apply. Удаление не выполнять без согласованного срока.
