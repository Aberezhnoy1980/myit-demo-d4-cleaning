# Режимы и доставка

**Актуальный срез — d4-tihiy-dom-sheets-b2-07 (06.11.2026):** офлайн-контракт Sheets, без новых установок/секретов/live.
Telegram принят в проверенном объёме: координатор провёл одну разрешённую отправку, получение/удаление подтверждены
владельцем (review-coordinator/telegram-b1-06/owner-confirmation.md). В B2 повторять Telegram не разрешено.

SheetsAdapter требует OfflineAuthorization/MockTransport; официальный SDK/OAuth ещё не реализованы и не проверены.
Существующий httpx 0.28.1 используется без дополнительных пакетов. Live CLI блокируется до config/data при отсутствии SDK,
а его появление не снимает блок до отдельной реализации/приёмки. Самописных JWT/OAuth/crypto нет.
Конфигурация только в отдельном будущем `.env.sheets`, пустой шаблон включён в срез; Telegram `.env` не читается.

Sheets: сохранённая неистёкшая синтетическая заявка → девять строковых значений A:I с исходным UTC → точная шапка
и ограниченный поиск UUID → RAW append при отсутствии → проверенный updatedRange → сравнение полного readback.
Лист Leads, до 200 строк данных/A2:I201, до 2 МиБ каждого чтения, без Drive/неограниченного сканирования.
Дубли/конфликт/полный или несвязный лист блокируют запись. Данные за пределом не исследуются, ресурс должен быть выделенным.

Claim/finalize в прежней схеме БД, тот же registry flock на один CLI UUID; ресурс/service account привязаны хэшем.
Максимум 3 отложенные явные попытки для безопасного pre-append отказа/валидного 429.
Неопределённость после append или сбой подтверждения/фиксации → unknown, новая запись блокируется.
Адресный reconcile делает только два GET и никогда POST, до 3 явных сверок. Отсутствие строки не разрешает append.
Ни один исход не меняет заявку/фото/Telegram. В квитанции каждый канал имеет независимый текст; жёсткая подпись
«Google Sheets не подключены» сохраняется только когда Sheets действительно отключён, а не для работающего канала.

Протокол/ограничения/SDK-предложение — sheets-b2/. Все B2 HTTP проверены офлайн на временных данных с запретом сокетов.
Настоящий SDK, скрытые refresh/retry и реальный ресурс требуют отдельной проверки после разрешённой установки.
Далее — описание принятой архитектуры Telegram; исторические утверждения об отсутствии live относятся к подготовке B1.

SQLite/restore/обработка фото основаны на независимо проверенном server-04. Заявка, JPEG и два задания
сохраняются одной транзакцией; квитанция ограничена случайным ключом/часом. По умолчанию оба канала not_connected.
HTTP-сохранение и старт сервера наружу ничего не отправляют.

`server/telegram.py` использует уже установленный httpx 0.28.1, только фиксированный HTTPS api.telegram.org/sendPhoto,
без redirect и доверия proxy-переменным окружения. Один JPEG из конкретной свежей заявки передаётся байтами.
Подпись содержит submission_id и параметры дивана, без контакта/ключа квитанции/свободного текста.
`server/telegram_config.py` читает только явно разрешённый локальный `.env`: три ключа из `.env.example`,
строгие права/владелец/размер, без shell и поиска других секретов. Два условия live: LIVE=1 и CLI `--execute-live`.

Команда `telegram-send --submission-id … --execute-live` предназначена только для будущего отдельно согласованного
одиночного теста. Она удерживает прежний registry flock, фиксирует processing до HTTP и результат после него.
Параллельный CLI/сервер/backup исключены; массового прохода очереди и фонового отправителя нет.
Смена получателя/бота после первой попытки блокируется. Схема БД не менялась: префиксы `mock_*`/`live_*`
и simulated разделяют режимы, безопасная служебная квитанция хранится в существующем приватном поле error.
Старые simulated=1 не превращаются в live. Клиенту доступны только канал/статус/режим, не config/provider metadata.

Connect/pool до передачи и валидный 429 допускают ручной отложенный повтор (всего максимум 3 попытки).
Неопределённость передачи/ответа/фиксации → unknown, повтор блокируется. Аварийный live_processing при следующей
адресной CLI-команде становится live_unknown без отправки; квитанция уже трактует processing как неизвестный результат.
Bot API success означает создание сообщения, не прочтение. Google Sheets и локальные данные не зависят от этого исхода.

HTTPX/httpcore logging исключается на время жизни HTTP-клиента; прежний logging.disable восстанавливается в finally.
Это краткое отключение стандартного logging в отдельном эксклюзивном CLI-процессе, не настройка всего web-приложения.
Полные Request/Response/Exception, URL с токеном и description не записываются в БД/вывод/протоколы.
Лимиты: connect 3 с, write/read 5 с, pool 1 с; response до 64 КиБ, без content-encoding,
15 с проверяются между чтениями. Это фазовые таймауты HTTPX, а не жёсткий системный лимит общего времени.

Пояснение тестового режима выводится отдельно для каждого simulated-канала по имени: тестовый Sheets не отрицает
подтверждённый/неизвестный результат Telegram. Повторная регрессия квитанции и JUnit — telegram-b1-06/;
подробный протокол адаптера — telegram-b1/, эксплуатация/будущая команда — README, ресурсы — live-resources.md.
Во всех B1-опытах HTTP заменён MockTransport и сеть запрещена, включая моделирование live-ветки на временных данных.
На этапе подготовки B1 реальных отправок не было; затем B1 был отдельно принят и испытан координатором (см. выше).
Sheets live и N4 целиком не закрыты.

Ниже сохранена историческая постановка первого прототипа, не описание текущей реализации.

Первый прототип: браузерная проверка → демонстрационный результат без сохранения.
Backend заявки отсутствует; SQLite/очередь/Telegram/Sheets не реализованы и не подключены.
Preview-сервер только раздаёт public. CSP `connect-src 'none'; form-action 'none'` запрещает отправки страницы.

Следующий согласуемый срез: проверка на сервере → транзакция SQLite (заявка + два независимых задания)
→ воркер → отдельные тестовые адаптеры Telegram/Sheets. Проверяемые статусы: accepted/pending/delivered/failed/unknown.
Неподключённые каналы не называются доставленными. Неопределённость после таймаута может означать дубль;
«ровно одна внешняя отправка» не обещается. Тело связано с ключом повтора; смена тела — конфликт.

Фото: до 3, JPEG/PNG/WebP, 5 МБ каждое, 12 МБ вместе, 20 Мп. Сейчас это только удобство клиентского ввода.
Следующий этап требует серверного определения формата, проверки декодирования с лимитами,
безопасного перекодирования без метаданных, случайных имён, закрытого хранения и уборки.
Клиентские MIME и проверки createImageBitmap не являются серверной безопасностью.

Локальный режим допускает только вымышленные контакты и безопасные тестовые фото.
Кандидат публичного режима: встроенная подготовленная синтетическая заявка/фото, без настоящих контактов и произвольных загрузок.
Публичный режим ещё не создан, текущий прототип не публиковать.

До live потребуется отдельное решение владельца: бот, закрытый Telegram-чат и разрешение получателя;
выделенная Google-таблица, разрешённый способ API-авторизации с минимальными правами;
безопасное хранение авторизации вне public/Git, среда, сроки хранения и квоты.
Никакие ресурсы не создавались, credentials коннекторов не читались, внешних отправок не было.
Файловые Drive/Яндекс Диск, VK/email/webhook сейчас не реализуются.
