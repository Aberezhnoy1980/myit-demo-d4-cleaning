# D4 · «Диван в порядке»

Локальный стенд лендинга вымышленной химчистки диванов. Услуги не оказываются.
Срез `d4-divan-v-poryadke-linked-10`: форма, два канала и раздельные статусы в квитанции.
Имя «Диван в порядке» и дескриптор «Химчистка диванов» утверждены в срезе `d4-divan-v-poryadke-rename-09`.
Дизайн, пользовательский путь, SVG-знак и папка d4-cleaning сохранены. Прежнее имя «Тихий дом» и идентификаторы
прошлых срезов остаются историей; офлайн-код основы — принятый `d4-tihiy-dom-sheets-b2-07`.
Локальное сохранение SQLite, обработка фото и квитанции реализованы; серверный этап/restore и офлайн B2 приняты
координатором в проверенном объёме. Это не приёмка всего публичного D4.
Telegram B1 принят в проверенном объёме, один тест проведён координатором и подтверждён владельцем
([свидетельство](docs/review-coordinator/telegram-b1-06/owner-confirmation.md)). Повторять Telegram для B2 запрещено.
Два канала проверяются в тестовом режиме на синтетических данных. Обычный запуск сохраняет заявку локально.

## Запуск

```sh
cd /Users/alex/myit/demo/Landing/d4-cleaning
.venv/bin/python tools/run.py --port 4344
```

Открыть <http://127.0.0.1:4344>. Остановка — Ctrl+C. Сервер слушает только loopback.
Проверенное окружение: macOS x86_64, Python 3.11.8, SQLite 3.45.1, Node 22.23.4 (только проверка JS).
Установлены ровно 24 разрешённых прикладных/тестовых пакета; фактические версии — requirements-lock-macos-py311.txt.
Pip 24.0 и setuptools 65.5.0 — bootstrap отдельного venv, глобальные пакеты не изменялись.
Сборки нет: публичные файлы только в `public/`. Backend не выдаёт DB, оригиналы фото, списки заявок и секреты.
Нужен существующий системный `/bin/ps` для контроля RSS собственного декодера. В песочнице без доступа к ps
декодирование безопасно отклоняется; тесты нужно запускать с этим доступом. Других инструментов не устанавливать.

Для воспроизведения окружения (установки уже разрешены 06.11.2026; существующий `.venv` не перезаписывать):

```sh
python3 -m venv .venv  # только если .venv отсутствует
.venv/bin/python -m pip --isolated install --index-url https://pypi.org/simple --only-binary=:all: -r requirements-lock-macos-py311.txt
.venv/bin/python -m pip check
```

Авторская копия согласованных constraints — constraints-macos-py311.txt, байты совпадают с файлом ревьюера.
Lock проверен на указанной платформе; поддержку других Python/OS не заявляем.
Альтернатива для согласованного набора: `-c constraints-macos-py311.txt -r requirements-test.txt`.
Команда `tools/serve.py` сохранена только для статического просмотра старых прототипов, API у неё нет.

Префикс, реально проверенный в браузере:

```sh
.venv/bin/python tools/run.py --port 4344 --prefix /d4
```

Открыть <http://127.0.0.1:4344/d4/>. Контакты, API URL и пути хранилища посетитель не настраивает.

## Безопасный показ

Актуальный сценарий и границы — [docs/demo.md](docs/demo.md). Для визуальной проверки без backend:
`.venv/bin/python tools/serve.py --port 4346` → <http://127.0.0.1:4346>, остановка Ctrl+C.
Статический preview не сохраняет заявки и не читает data/.env; для реального локального сохранения нужен запуск выше.

1. Только локально. Никаких настоящих контактов, адресов, личных фото.
2. Главная кнопка прокручивает к форме. Пустая проверка показывает ошибки и переводит фокус на их список.
3. Нажать «Заполнить тестовым примером» либо ввести параметры и добавить безопасное тестовое фото.
4. Контакт — `demo@example.test` либо Telegram `@demo_test`. Другие домены и имена намеренно отклоняются.
5. «Сохранить тестовый запрос» проверяет поля/фото сервером и сохраняет заявку. Квитанция честно отделяет сохранение от доставки.
6. Фото можно удалить; поля остаются при возврате. Повтор неизменённой формы после разрыва связи не создаёт дубль.
7. «Проверить квитанцию» читает только свою заявку по случайному ключу на 1 час; ключ хранится в памяти страницы.
   После перезагрузки доступ к квитанции теряется, сама заявка остаётся до очистки. Не помещать ключ в URL/логи/доказательства.

Произвольные фото допустимы здесь только для закрытого теста. Этот режим не подходит для публичного выпуска.
Кандидат публичного демо должен работать с заранее подготовленной заявкой и встроенным безопасным фото.

## Данные, лимиты и эксплуатация

`data/registry.sqlite3` — закрытая SQLite с заявками, перекодированными JPEG BLOB и двумя заданиями доставки.
Эти три части сохраняются одной транзакцией. Отдельных постоянных uploads/оригиналов нет.
Multipart временно использует системную временную папку; файлы закрываются и удаляются после чтения/ошибки.
Имена и пути посетителя не используются в хранении; внутренние имена случайные. `data/` имеет права 0700, DB — 0600.
Локальные данные, `.env`, `.venv`, uploads и backups исключены из Git/manifest и лежат вне public.

Лимиты: 1–3 фото, JPEG/PNG/WebP; 5 МиБ каждое, 12 МиБ суммарно; тело запроса до 13 МиБ, до 10 секунд чтения;
20 млн пикселей/фото, статическое изображение. MIME должен совпасть с декодированным форматом.
Каждое фото обрабатывается в отдельном процессе: CPU 3 секунды, стеновое время 6 секунд, RSS watchdog
384 МиБ с выборкой 100 мс; максимум два декодера и два запроса одновременно. Это не мгновенный kernel memory limit:
Darwin отклонил RLIMIT_DATA/AS, возможен краткий выход за RSS-порог между выборками. Пиксели ограничены до декодирования.
Выход — новый JPEG до 2000×2000 без EXIF/ICC/XMP и исходного имени. SVG/HTML/GIF/анимации не принимаются.

5 попыток POST в минуту, 30 в час на весь локальный стенд; счётчики переживают перезапуск.
Предел реестра — 200 заявок или 100 МиБ фото; переполнение даёт 507 без частичной записи.
Ключ повтора связан с нормализованными полями, MIME и SHA-256 исходных байтов фотографий, порядок учитывается.
Новые multipart boundary/имена файлов не меняют смысл запроса. Другие поля/байты с тем же ключом дают 409.
Повтор также учитывается в лимите попыток: при 429 дождаться разрешённого повтора, не менять данные ради обхода.

Срок заявки/ключа повтора — 24 часа. Очистка выполняется при старте и каждые 60 секунд работающего сервера;
при выключенном сервере данные физически сохраняются до следующего запуска/ручной очистки.
Квитанция истекает через час независимо от cleanup. После удаления заявки старый ключ может создать новую.
Настоящие секреты не проверялись и не читались. Подготовленный B1 читает только конкретный исключённый `.env`
явной командой после отдельного разрешения; окружение/Keychain и конфигурации других демо не использует.

## Backup, восстановление, очистка и тестовая доставка

Сначала остановить сервер. Все команды администратора берут тот же эксклюзивный lock и отказывают, если сервер запущен.

```sh
.venv/bin/python -m server.manage backup
.venv/bin/python -m server.manage cleanup          # только перечень количества истёкших записей/backup
.venv/bin/python -m server.manage cleanup --apply  # удаляет истёкшие заявки с фото/заданиями и backup старше 24 ч
.venv/bin/python -m server.manage restore ИМЯ.sqlite3
```

Backup создаётся SQLite backup API в `backups/` (0700), файл 0600. Это локальная копия, не удалённая страховка.
Restore принимает только имя существующего файла внутри backups и сохраняет отдельную safety-copy текущего реестра.
Совместимость проверяется на приватном временном снимке: integrity, точная схема D4 (колонки, ограничения,
индексы/триггеры), параметры SQLite и foreign keys. Поддерживаются backup штатного формата D4;
похожая схема другой версии не мигрируется автоматически.
Initialize/recovery и очистка истёкших записей выполняются на подготовленном снимке **до** записи в текущую базу.
Затем SQLite Backup API переносит его одной транзакцией; ошибка между страницами откатывает перенос.
После commit нет дополнительной инициализации или очистки рабочего реестра. CLI при отказе возвращает код 2;
safety-copy остаётся приватно, но работоспособность исходного реестра не зависит от её ручного восстановления.
Backup также содержит закрытые поля/ключи:
не переносить его в public/Git/артефакты ревью. Срок backup — 24 часа, удаление командой cleanup, не фоновым заданием.

Только имитация, без HTTP-транспорта и credentials:

```sh
.venv/bin/python -m server.manage simulate --channel telegram --scenario timeout
.venv/bin/python -m server.manage simulate --channel sheets --scenario success
```

Допустимы success/unavailable/rate_limit/timeout/forbidden. Команда переводит неподключённые задания в тестовый
режим и делает один шаг указанного канала. Максимум 3 попытки; retry с задержкой 30 с, rate limit — 60 с.
Unknown после таймаута/остановки processing не повторяется автоматически. В квитанции тест не называется живой доставкой.

## Telegram B1: принят, разрешение одного теста исчерпано

Координатор независимо принял B1-06, провёл один разрешённый live-тест; владелец подтвердил получение и удаление.
Последнее проверенное координатором состояние LIVE=0, сервер остановлен. Исполнитель B2 настоящий `.env` не проверяет.
Ниже сохранён интерфейс B1 для эксплуатации: каждая новая живая операция требует нового явного разрешения.

Шаблон — [.env.example](.env.example): только пустые `D4_TELEGRAM_TOKEN`, `D4_TELEGRAM_CHAT_ID`
и `D4_TELEGRAM_LIVE=0`. При импорте, запуске сервера и HTTP-сохранении он не читается, отправок нет.
`httpx==0.28.1` уже входил в согласованные 24 пакета; новых установок для B1 не выполнялось.

После независимого ревью и **отдельного разрешения владельца на конкретную операцию**:

1. Владелец локально готовит `/Users/alex/myit/demo/Landing/d4-cleaning/.env` по шаблону, с правами 0600
   (также поддерживаются 0400), без symlink. Токен и ID не передаются в чат/argv. Парсер принимает только три ключа
   шаблона, буквальные значения без кавычек, `export`, shell/source/eval и подстановок. Live требует значения `1`.
2. Согласовать одну свежую синтетическую заявку и первый подготовленный JPEG из неё; получатель — одна закрытая группа.
   Создать заявку через локальную форму, сохранить её ID и квитанцию в памяти вкладки, остановить сервер.
   Старые simulated-задания для этого не подходят, их нельзя преобразовать в live.
3. Выполнить ровно один согласованный запуск, заменив только `ОДИН_СОГЛАСОВАННЫЙ_UUID`:

```sh
cd /Users/alex/myit/demo/Landing/d4-cleaning
.venv/bin/python -m server.manage telegram-send --submission-id ОДИН_СОГЛАСОВАННЫЙ_UUID --execute-live
```

Без `--execute-live` команда завершается до чтения конфигурации; при пустой/выключенной/ошибочной настройке — до сети.
CLI держит тот же эксклюзивный registry lock во время проверки, отправки и фиксации результата.
Второй отправитель, web-сервер, backup/restore и другие административные команды одновременно не работают.
`send_one` — внутренний метод с обязательным lock вызывающей стороны, не публичный endpoint/воркер.

Только HTTPS `api.telegram.org`, `sendPhoto`, без redirect/proxy из окружения. Отправляются байты одного закрытого JPEG,
ID заявки и краткие синтетические параметры; контакт, свободный текст, публичный URL и ключ квитанции не отправляются.
Получатель/бот привязываются к заданию при первой попытке; HTTP-посетитель их не выбирает.
Статусы `mock_*`/`live_*` и флаг simulated разделяют режимы; квитанция показывает режим и безопасный смысл результата.
Sheets остаётся not_connected, заявка и фото сохраняются.

Connect/pool отказ до передачи: только ручной повтор спустя 30 с; явный валидный 429 — спустя retry_after (1–3600 с).
Всего до 3 попыток на задание, автоматических повторов нет. Таймаут/обрыв после возможной передачи, неверный ответ,
сбой фиксации результата или оставшийся после аварии processing → unknown и блокировка повтора.
200 подтверждает создание сообщения только при проверенном получателе/message_id/фото; прочтение человеком не подтверждает.
Повтор уже подтверждённой команды не вызывает Bot API снова. Telegram exactly-once не обещается.

Владелец отдельно подтверждает сообщение с тем же ID в группе; при unknown сначала проверяет группу, команду не повторять.
План подтверждения, хранения и очистки — [docs/telegram-b1/acceptance.md](docs/telegram-b1/acceptance.md).
В этой передаче B2 команда выше с реальными ресурсами **не запускалась**.

## Sheets B2 и проверка связки

Тестовый режим включается через `create_app(settings, test_delivery=(telegram, sheets))`.
Оба канала используют MockTransport, Sheets получает токен через google-auth с искусственным ключом
и отдельным подставным OAuth-транспортом. Официальный SDK берётся из подготовленного окружения VM.
Форма сохраняет заявку, фото и два задания одной транзакцией. После коммита HTTP-ответ даёт номер и статусы ожидания.
Фоновый обработчик берёт два задания этой заявки. Кнопка «Проверить квитанцию» читает результат каждого канала.
Повтор формы возвращает прежний номер. При старте прерванная тестовая обработка получает неопределённый статус.
Сценарии и команды офлайн-проверки описаны в [протоколе связки](docs/linked-10/acceptance.md).

Строка A:I: submission_id, accepted_at_utc, sofa, size, material, description, synthetic_channel,
synthetic_contact, photo_count. UTC берётся из сохранённой заявки, значения RAW, формульный текст не преобразуется.
Проверяются точная шапка Leads!A1:I1, UUID в Leads!A2:I201 и все 9 значений после append.
200 строк данных — конечный предел; дубли/конфликты/дырки/переполнение требуют разбора без перестройки листа.
Одна полностью совпавшая строка подтверждается без POST. Чужой updatedRange не становится URL.

Новый адресный интерфейс на один UUID (пока даёт только безопасный отказ, **не запуск живого теста**):

```sh
.venv/bin/python -m server.manage sheets-send --submission-id ОДИН_СОГЛАСОВАННЫЙ_UUID --execute-live
.venv/bin/python -m server.manage sheets-reconcile --submission-id ТОТ_ЖЕ_UUID --execute-live
```

Без флага нет чтения настройки; отсутствие SDK останавливает до config/data/сети.
Даже установка SDK сама по себе live не включит: сначала отдельная реализация и приёмка авторизации.
Будущий источник — только явный service_account JSON согласованной учётной записи по фиксированному приватному пути
из шаблона, без ADC/окружения/Keychain fallback. Сейчас ключ и каталог `.secrets/` не создавались/не читались.

Команды держат прежний эксклюзивный registry flock. Тестовые задания не повышаются в live, ресурс/service account
привязываются при первом claim; ротация ключа той же учётной записи не создаёт дубль.
До append сетевой отказ или явный валидный 429 допускают ручную отложенную попытку, всего до 3.
Явный 400/401/403/404 или истёкшая авторизация дают отказ, без автоматического refresh/replay.
Неопределённость после append, любой сбой подтверждающего чтения или фиксации результата → unknown, повтор записи запрещён.
Reconcile делает только ограниченное чтение (до 3 явных сверок): совпадение подтверждает строку,
отсутствие/дубли/конфликт не дают права append. Заявка/фото и Telegram независимы от Sheets.

[Предложение зависимостей](docs/sheets-b2/dependencies.md) содержит точные версии/полный метаданный набор,
ограничения Intel/macOS и план проверки SDK. Это не установленный lock и не разрешение установки.
[Протокол](docs/sheets-b2/acceptance.md) отделяет 98 выполненных B2-проверок от непроверенного SDK/OAuth.
Ресурсы/шапка/права и будущая очистка — [docs/live-resources.md](docs/live-resources.md).
